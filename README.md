# AI开发的教育账：调度教的是公平，显存教的是约束，泄漏教的是责任

在高校和职业院校教AI开发，这三件事的定位和工业界完全不同。工业界关心成本和效率，教育场景关心的却是另一套东西：几十个学生同时上机时，资源怎么分才不打架；显存有限时，怎么让学生理解“约束下的工程”；以及当一个学生把卡跑崩了，怎么让他真正记住什么叫“负责任地写代码”。以下是我从教学视角的一些观察。

**资源调度：课堂本身就是资源分配的示范**

教育场景的资源调度有个天然矛盾：学生需要动手，但硬件永远不够人手一张卡。昇腾社区的一篇技术实践直接点出了这个痛点——教育AI实训对性能要求不高，但对成本敏感，通常需要单卡同时跑不少于八个实训任务。他们的解法是用时间片轮转做算力切分，单卡支撑多学生并发。

从教学角度看，这其实比“人手一卡”更有价值。学生提交任务后看到排队、看到自己的资源配额、看到别人在用，这本身就是对“共享环境下的资源调度常识”最直观的建立。职业院校的实践里有个细节我很认同：平台设资源监控页，学生能看到自己任务占了多少显存和时长，资源意识由此建立——不是无限调用，而是学会在小算力上做减法。课堂里教调度，教的不是算法，是“你的代码要排队”这个事实。

**显存优化：约束是最好的老师**

工业界做显存优化是为了省钱，教育场景做显存优化是为了让学生“在有限条件下把事做成”。某高校实验室用二十四G显存的卡跑模型，学生一开始总想调大batch size，直到OOM报错反复出现，才开始认真理解batch、激活值和显存之间的三角关系。有实训平台的设计思路很务实：限制单任务显存，学生自然学会用更小的批量换吞吐，资源约束逼出工程意识。

我见过的最好的教学案例，是让学生亲手制造一次显存泄漏然后自己修。某高校计算机视觉实验室的ResNet训练中，显存从十二G逐轮涨到二十二G崩溃，排查后发现数据加载没释放PIL图像、训练循环没清理中间变量。学生做完这个实验后的反馈是：比听十遍“要注意内存管理”都管用。显存优化的教学价值恰恰在于它的“不自由”——当你只有二十四G，你才会真正思考每一兆花在了哪里。

**泄漏排查：让学生经历一次“自己造成的崩溃”**

显存泄漏在教育场景里有个特殊优势：它是最安全的犯错方式。学生把卡跑崩了，重启就好，代价只是几分钟排队。但那个“为什么越跑越慢”的困惑，会逼着他去理解计算图的生命周期、缓存机制、引用持有这些平时讲课没人听的细节。

实训平台的设计者也意识到了这一点。有云原生教学方案把“极易发生显存泄漏导致集群崩溃”列为核心痛点。但换个角度看，泄漏不是要消灭的敌人，而是最好的教学素材。我个人的建议是：在课程里专门设一个“故意泄漏”的环节，让学生用`nvidia-smi`看着显存逐轮上涨，然后自己定位是数据加载、训练循环还是验证阶段的问题。修复后的显存曲线变平的那一刻，比任何考试分数都能说明他学会了。

**写在最后**

教育场景和工业场景对这三件事的诉求正好互补。工业界要的是“别出事、别多花钱”，教育要的是“出事了能学会”。调度教的是共享意识，显存教的是边界意识，泄漏教的是排查纪律。一个学生在毕业前经历过一次自己造成的OOM、亲手定位过一个泄漏点、在排队中理解了别人也在用同一张卡，他进入工业界时的起点，比只会调模型结构的同学高出一截。
